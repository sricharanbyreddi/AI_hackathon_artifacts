How to Read the Matrix

Column Meaning
Req‑ID Unique identifier (FR = Functional, NFR = Non‑Functional, AI = AI‑specific).
Requirement Concise statement of what must be delivered.
User‑Story / Use‑Case Reference The high‑level story that drives the requirement (e.g., US‑001 = “CFO wants a single view of material exceptions”).
Test‑Case(s) Mapping One or more test‑case IDs that verify the requirement. Positive (POS), Negative (NEG), Low‑Confidence (LOWCONF), Performance (PERF), Security (SEC), etc.
Verification Method How the test is executed (functional test, load test, security scan, audit, etc.).
Status Current lifecycle stage – Draft, Reviewed, Approved, Implemented, Validated, Closed.

Traceability Flow (High‑Level)

flowchart LR
    US[User Stories] --> FR[Functional Requirements]
    US --> NFR[Non‑Functional Requirements]
    US --> AI[AI Requirements]
    FR --> Design[Design Artifacts (UML, Wireframes, Data Model)]
    NFR --> Design
    AI --> Design
    Design --> Code[Source Code Modules]
    Code --> TC[Test Cases]
    TC --> TestExec[Automated Test Execution]
    TestExec --> Verif[Verification & Sign‑off]
    Verif --> RTM[Requirement Traceability Matrix]
    Verif --> Demo[Demo Package]
    Verif --> Docs[Documentation (Manuals, Prompt Register)]

The matrix is the single source of truth linking User Stories → Requirements → Design → Code → Tests → Evidence. Any change to a requirement must trigger a traceability impact analysis (governed by the Change Management process).

All artefacts (RTM, design docs, code, test suites, prompt register) are stored in the Spendid_project Azure DevOps repository with branch protection, mandatory pull‑request approvals, and immutable tags for released versions.
